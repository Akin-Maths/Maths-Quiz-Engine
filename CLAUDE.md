# GCSE Maths Quiz Templating Engine — project memory

This file is written so a fresh Claude Code session (or any other assistant/developer)
can pick up this project with no prior context. It was generated by Claude
(via Cowork) after a long working session building and fixing this engine for
Tayo, a UK secondary maths teacher. Read this whole file before making changes.

## What this is

A single-page web app that generates printable/projectable GCSE maths quizzes.
A teacher ticks subtopics (e.g. "Solve quadratics by factorising"), picks a
quiz length and practice mode, and the app generates fresh, randomly-seeded
questions with a full worked mark scheme, laid out for A4 printing (3
questions per page) in three swappable "versions" (V1/V2/V3, e.g. for
different classes or retests). It also has a separate, fixed-format
"Negative Numbers Speed Check" fluency sheet.

There is **no backend, no build step, no npm bundler for the shipped
artifact**. The whole app ships as one static HTML file that a teacher can
open directly in a browser or host on GitHub Pages.

## Architecture

**No JSX transpiler/bundler is used for the shipped file.** `quiz_engine.html`
loads React 18 (UMD), ReactDOM 18 (UMD), and Babel Standalone from CDN, then
contains a `<script type="text/babel" data-presets="react">` block with a
lightly-transformed copy of `QuizEngine.jsx`'s contents, compiled to plain JS
**in the browser, on every page load**. This is why there's a `tools/build.js`
step (below) instead of a normal `npm run build` — it isn't compiling to a
bundle, it's just keeping that inlined `<script>` block in sync with the
source file. The transform is mechanical: strip the `import React ...` line
(React is a global from the CDN `<script>` tag instead), destructure the
hooks used (`useState`, `useMemo`, `useCallback`, `useId`, `useEffect`,
`useRef`) since Babel Standalone doesn't know to rewrite bare hook calls into
`React.useX`, strip `export default` (no module system in a `<script>` tag),
and append `ReactDOM.createRoot(...).render(<QuizEngine />)` to mount it.

### Build & verify

A `tools/` folder was added at the end of this session with the scripts below.
Run `npm install` inside `tools/` once (needs `@babel/core` and
`@babel/preset-react`) before using them.

- **`node tools/build.js`** — rebuilds `quiz_engine.html` from `QuizEngine.jsx`
  (the transform described above). Run this after every edit to the .jsx.
- **`node tools/build.js --check`** — Babel-compiles the transformed source
  and reports a syntax error if there is one, without writing anything. Fast
  sanity check before a full rebuild.
- **`node tools/fuzz3.js`** — loads `SUBTOPIC_BANK` out of `QuizEngine.jsx`
  (via an in-memory Babel compile + a tiny sandboxed React stub — no real DOM,
  no browser needed) and calls every subtopic's `build(rng)` function across
  many seeds, deep-walking the returned prompt/answer/render element trees for
  thrown errors or leaked `NaN`/`Infinity`/`undefined`. A clean run ends with
  `NO BAD ATTRIBUTES / ERRORS FOUND.` and `Bad FULL_SPEC paths: 0`. Current
  baseline: 344 ids, 13,760 (id, seed) combos, 0 bad paths.
- **`node tools/cosmetic_scan.js`** — same loading trick, but instead scans
  the rendered prompt/answer text for cosmetic-bug patterns: a literal `1x`/
  `-1x` instead of `x`/`-x`, a `^1` exponent that should've simplified away, a
  stray `+ 0`/`- 0` term, or an uncollapsed double sign like `+ -`. **This is
  not a pass/fail gate** — see "Known issues" below, there is a large
  pre-existing backlog of real matches. Use it to check that an edit didn't
  introduce a *new* instance of one of these patterns, by diffing its output
  before/after your change, not by expecting the total to hit zero.
- There is **no bundled browser/UI test suite** in this repo. During this
  session, UI behaviour (drag-to-reorder, the timer, delete/tick interactions,
  quiz-code save/reload, etc.) was verified with ad hoc Playwright scripts
  run against a local copy of `quiz_engine.html` with the CDN script tags
  swapped for local `node_modules` paths (Playwright's browser automation
  can't fetch from a real CDN in a sandboxed environment). Those scripts were
  written against a specific sandbox's Chromium path and aren't portable as-is,
  but the pattern is straightforward to recreate with a normal
  `npm install -D playwright` + `npx playwright install chromium` if
  browser-level regression testing is wanted going forward: open
  `quiz_engine.html` (CDN links work fine on a normal machine with internet
  access, so no swapping needed), expand every subtopic accordion, tick/untick
  checkboxes and click buttons via `page.locator(...)`, and assert on the
  rendered `.quiz-question` elements.

## Data model

- **`SUBTOPIC_BANK`** (currently 344 entries) — the heart of the app. Each
  entry is `{ topic, title, marks, build(rng) => ({ prompt, answer, render?,
  answerRender? }) }`. `build` takes a seeded RNG and returns everything
  needed to render one instance of that question type. `render`/
  `answerRender` are optional inline-SVG React elements for diagram
  questions.
- **`FULL_SPEC`** / **`SUBTOPIC_TO_SPEC`** — the curriculum tree (Strand →
  Domain → Group) used to organise the sidebar topic picker, and each
  subtopic id's path into that tree. Must stay in sync with `SUBTOPIC_BANK`
  (checked by `fuzz3.js`).
- **Helper functions** for formatting signed terms: `pm(n, sym)` (no leading
  space), `pm0(n, sym)` (leading space, omits the term entirely when `n===0`),
  `coefX(m, sym)` (a coefficient-aware version that correctly special-cases
  `±1` as `x`/`-x` rather than `1x`/`-1x`), `gcd(a,b)`.
  **Known gotcha:** `pm`/`pm0` do NOT special-case a magnitude-1 coefficient —
  `pm0(1, "x")` renders `"+ 1x"`, not `"+ x"`. Several subtopics call `pm0`
  directly instead of `coefX` and produce the literal-`1x` bug as a result.
  See "Known issues" below — this is the single biggest thing worth fixing
  next.
- **`ALL_SUBTOPIC_IDS = Object.keys(SUBTOPIC_BANK)`** — kept only for
  decoding pre-existing shareable quiz codes that used positional indices
  into this array (see "Quiz codes" below). Never add new code that indexes
  into this array — subtopic ids are the stable identifier now.

## Quiz-building state (in `QuizEngine()`)

- **`selected`** — array of ticked subtopic ids. In Do Now (4)/Weekly Quiz (6)
  modes this is always a set of *unique* ids, cycled to fill the fixed
  length. **In Custom mode it's a genuine multiset** — the same id can appear
  more than once, once per "copy" the teacher asked for via the per-topic
  +/− stepper next to each ticked topic in the sidebar. This was a deliberate
  redesign partway through the session (see changelog) — earlier, Custom mode
  had a single "Number of questions" field and cycled through whatever was
  ticked to fill it; that's gone now, replaced by per-topic counts that sum
  to the total.
- **`lengthMode`** — `"donow" | "weekly" | "custom"`. Drives which UI is
  shown and, in Custom mode, materially changes how `selected` is
  interpreted (see `effectiveIds` below) — it's not just a display flag.
- **`quizLength`** — the fixed length (4 or 6) for Do Now/Weekly Quiz presets.
  Vestigial for Custom mode (which derives its total from `selected.length`
  instead) but still used as a sane starting value if the teacher switches
  back to a preset.
- **`effectiveIds`** — for Do Now/Weekly, cycles `selected` (via `i %
  selected.length`) to fill `quizLength` slots. **For Custom mode, it's just
  `selected` directly — no cycling at all** — since `selected` already
  contains one entry per question slot.
- **`toggleSubtopic(id)` / `setTopicCount(id, n)`** — in Custom mode, ticking
  a checkbox is `setTopicCount(id, 0-or-1)`; the +/− stepper calls
  `setTopicCount` directly for counts beyond 1. `setTopicCount` inserts/
  removes copies of `id` right after its existing block in `selected` (so a
  topic's questions stay grouped in the generated quiz) and caps the overall
  list at 60 entries.
- **`deleteQuestion(index)`** — in Custom mode, removes exactly the one
  entry at that position from `selected` (decrementing that topic's count by
  one — NOT wiping every copy of it). In Do Now/Weekly mode, unticks the
  subtopic entirely and lets the fixed length refill by cycling whatever's
  left ticked. There is deliberately **no separate "hidden question" list**
  (an earlier `removedIndices` state was removed) — driving deletion
  entirely off `selected` was the fix for a bug where ticking any topic would
  silently resurrect previously-deleted questions.

## Quiz codes (shareable "?code=" links / paste-a-code box)

There's no backend, so a "quiz code" self-encodes everything needed to
reproduce a quiz (subtopics, mode, length, RNG salt, active version) as a
compact string — see `encodeQuizCode`/`decodeQuizCode` near the top of
`QuizEngine.jsx`. Two things worth knowing before touching this:

1. **The body encodes literal subtopic-id strings** (joined by `~`, since ids
   themselves contain `-`), not positional indices — this was a deliberate
   fix this session. The original design encoded positional indices into
   `ALL_SUBTOPIC_IDS`, which silently broke any previously-saved code the
   moment a new subtopic got inserted anywhere in the middle of
   `SUBTOPIC_BANK` (which happened several times this session) — every index
   after the insertion point shifted, so an old code would decode to the
   *wrong* subtopics with no error. A `formatVersion` header field
   distinguishes the two encodings; codes without it (or with an older
   value) fall back to the legacy index-based decode. **Any code saved
   before this fix may already be corrupted this way — there's no way to
   recover it after the fact.** Never reintroduce positional-index encoding.
2. **`lengthMode` in the header is derived from `lengthCode` directly, not
   from the numeric length value.** An earlier version inferred
   donow/weekly/custom by checking `length === 4` / `length === 6`, which
   silently misfired for a *Custom* quiz whose count happened to be exactly
   4 or 6 (it would reload as a Do Now/Weekly Quiz instead of Custom). Both
   `encodeQuizCode` (writing `lengthCode`) and `decodeQuizCode` (returning an
   explicit `lengthMode` field) must stay driven by the actual UI mode, never
   by sniffing the count.

  "type any number of questions" (first pass) and then to today's per-topic

  reproducing the same quiz. All three root causes and fixes are described

  teacher can ask for "3 of this question" per topic instead of one tick
  always meaning one question, while fixing a related quiz-code ambiguity
  (Custom counts of exactly 4/6 misfiling as Do Now/Weekly on reload).

  teacher was viewing a much older, unrelated snapshot (`quiz_engine_46.html`)
  and asking how to get faster iteration going forward.

## Known issues / good next tasks

1. **`index.html` currently links to `quiz_engine_46.html`, a stale snapshot
   from very early in this session** — it's missing essentially everything
   in the changelog above. If this repo is what's deployed (e.g. GitHub
   Pages), **the live site is serving a very outdated version of the quiz
   engine.** Worth confirming with the teacher whether to refresh
   `quiz_engine_46.html` from the current `quiz_engine.html`, or repoint
   `index.html` at `quiz_engine.html` (or a newly-numbered version) directly.
2. **Widespread pre-existing `1x`/`-1x` and stray `+0`/`-0` formatting bugs**,
   found by running the new full-bank `tools/cosmetic_scan.js` (1,282 matches
   across many subtopics that predate this session — things like
   `linear-graph-two-points`, `quadratic-sequences`,
   `inequality-both-sides`, `vectors-parallel-proof`, and dozens more). These
   were never caught before because the old cosmetic-check script only ever
   scanned the specific ids added *during* this session, never the
   pre-existing bank. The root cause is almost certainly that many
   `build()` functions call `pm0()` directly for a coefficient instead of
   the `±1`-aware `coefX()` (see "Data model" above) — fixing the shared
   helper(s), or auditing call sites that should use `coefX` instead of
   `pm0`, would likely resolve most of these in one pass rather than needing
   344 individual patches. **Not fixed in this session** — flagged here as
   the most valuable next piece of work.
3. A code saved before the id-string quiz-code fix (see "Quiz codes" above)
   may already decode to the wrong subtopics; this can't be repaired
   retroactively.
4. The `file:///...` text a teacher may see stamped on every printed/PDF
   page is the *browser's* print header/footer (URL + date), not anything in
   this app — there's no in-page fix; it's toggled off via the print
   dialog's "Headers and footers" option (Chrome: Print → More settings).
5. GitHub Pages requires the literal filenames `index.html`/whatever
   `index.html` links to — a browser silently renaming an upload to
   `name (1).html`/`name_1.html` (e.g. because a same-named file was already
   downloaded) causes a 404 with no obvious error. If a deploy stops working,
   check the exact filenames in the GitHub repo first.
